Change api-envio-smtp · Generado el 2026-07-11

El change añade el núcleo de envío del backend: el endpoint POST /api/send que recibe el correo en JSON y lo entrega a un servidor SMTP con Nodemailer, y el registro en logs del resultado sin contenido ni secretos. Cubre HU-03 (envío) y HU-04 (logging), fase 2 del roadmap.

#Supuestos y huecos

  • Supuesto: el consumidor del endpoint en esta fase es un cliente HTTP genérico (curl o la futura UI de la fase 4); aún no existe integración con el frontend.
  • Supuesto: en desarrollo el servidor SMTP es Mailpit (host mailpit/localhost, puerto 1025, sin auth ni TLS); en real es un proveedor configurable por env.
  • Hueco: no hay validación de dominio ni saneamiento en esta fase (decisión de pre-flight); llegan en HU-18 (fase 5) y HU-17 (fase 7). Un JSON mal formado lo rechaza el parser de Express con 400.
  • Hueco: sin adjunto ni multipart/form-data (fase 6, HU-11–13).

#Casos de uso

El actor principal es quien dispara el envío contra el endpoint; el servidor SMTP es el sistema secundario que entrega el correo. El logging acompaña a todo intento de envío.

#Actividad

Flujo del pipeline de POST /api/send: parseo del JSON, envío con Nodemailer y registro del resultado, con la rama de error controlado ante fallo del SMTP. Sin validación de dominio ni saneamiento en esta fase.

#Secuencia 1 - Happy path

Envío con datos válidos y SMTP disponible: el correo se entrega y se responde éxito, registrando destinatarios y asunto sin el cuerpo.

#Secuencia 2 - Fallo del SMTP

El servidor SMTP rechaza o no está disponible: el endpoint responde un error controlado sin filtrar credenciales y deja traza del error.

#Estado

Ciclo de vida de una petición de envío dentro del pipeline, desde su recepción hasta la respuesta de éxito o error.

Change foundation · Generado el 2026-07-11

El change foundation levanta el walking skeleton del proyecto: monorepo Turborepo + pnpm con apps/web, apps/api y packages/shared. Soporta dos modos de arranque: full con Docker Compose (web + api + Mailpit) y nativo para desarrollo (pnpm dev para web+api, con Mailpit siempre en Docker). Expone GET /api/health, configura el harness de tests y carga la config por variables de entorno con dotenv. No incluye lógica de negocio (formulario, envío SMTP, validaciones).

#Supuestos y huecos

  • Supuesto: el actor humano relevante es el Equipo de desarrollo (rol enabler de F0); el remitente final no interviene en esta fase.
  • Supuesto: la máquina de estados se modela sobre el arranque del entorno local (no hay entidad de dominio con ciclo de vida en foundation).
  • Supuesto: docker compose up orquesta web, api y mailpit (modo full); el modo nativo arranca solo mailpit en Docker (docker compose up -d mailpit) y web+api con pnpm dev.
  • Supuesto: el despliegue es solo Docker (NFR-08); el modo nativo es exclusivamente el inner-loop de desarrollo.
  • Hueco: proveedor y credenciales SMTP de producción pendientes (no bloqueante; en dev se usa Mailpit). Heredado de arquitectura-base.md §13.
  • Hueco: packages/shared se crea con estructura mínima; el contrato de email real llega en fases posteriores del roadmap.

#Casos de uso

El equipo de desarrollo instala el monorepo y puede arrancar en dos modos: full con Docker Compose, o nativo con pnpm dev dejando la infra en Docker. Ambos include la verificación del skeleton vía health-check.

#Actividad

Flujo desde la instalación hasta la verificación, con bifurcación por modo de arranque. En full, Docker orquesta los tres servicios; en nativo, Docker solo levanta Mailpit y la app corre con pnpm dev. Si falta una variable requerida, la validación de config (Zod) aborta el arranque del backend.

#Secuencia 1 - Happy path: arranque y verificación

Precondición: .env presente con las variables requeridas y Docker disponible. El desarrollador arranca el entorno y verifica el health-check contra el backend.

#Secuencia 2 - Inner-loop nativo con infra en Docker

Precondición: .env presente con valores de dev (SMTP_HOST localhost). El desarrollador levanta solo Mailpit en Docker y arranca la app nativa con pnpm dev.

#Secuencia 3 - Configuración de entorno inválida

Escenario alternativo: falta una variable de entorno requerida. La validación con Zod falla al arrancar y el backend no queda en estado inconsistente.

#Estado

Ciclo de vida del arranque del entorno local, con dos vías (full y nativo) que convergen en el estado operativo. No hay entidad de dominio en foundation; se modela el estado del skeleton desde la instalación hasta operativo.
